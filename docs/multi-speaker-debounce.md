# 多人消息防抖与同步规则

## 当前统一配置

测试窗口和 QQ 运行层必须使用同一组消息收集参数：

- **按发言者独立分线**：以昵称（测试窗口）或 `sender_id`（QQ）建立独立队列，不能让甲的消息等待或覆盖乙的队列。
- **静默等待**：同一发言者最后一条消息后等待 **2 秒**。2 秒内继续发来的内容进入该发言者的候选批次。
- **最长收集时间**：从该发言者第一条消息开始计算，最多收集 **3 秒**；到时立即结束本批。
- **同话题判断**：先由本机轻量规则依据承接词和文本主题重叠分组，不额外调用 Luna。模型只负责已分好的批次中的理解、回复和最终表达。
- **同话题合并**：同一发言者的连续同话题消息可以合并；不同发言者的消息只有在同一时间窗口且主题明显相近时才可合并，事件和身份仍分别保留。
- **分别回复**：话题不同、对象不同或超过 3 秒才到达的消息必须拆成独立批次，分别绑定各自消息事件。
- **回复上限**：同一模型回合最多分别处理 3 个独立目标，避免多人刷屏放大调用量。

## 两端对应位置

| 端 | 实现位置 | 关键配置 |
| --- | --- | --- |
| 测试窗口 | `dialogue-test-window/index.html` | `queueSpeaker()` 中的 `2000`，`3000` 最大收集时间 |
| QQ 运行层 | `luna-chat-runtime.py` | `FRAGMENT_QUIET_SECONDS = 2.0`，`wait_for_input(..., fragment=True)` 使用 3 秒上限 |
| QQ 合并判断 | `chat_social.py` | `should_coalesce()` 只决定是否进入连续消息收集，不替代对象分线 |
| QQ 事件路由 | `conversation_packet.py`、`chat_context.py` | `sender_id`、`event_id`、引用与 @ 目标分别保留 |

## 修改同步要求

任何涉及以下内容的修改，都必须同时检查测试窗口和 QQ 运行层：

1. 静默等待秒数
2. 最长收集时间
3. 按发言者分线规则
4. 同话题合并规则
5. 超时后的拆分与回复队列

修改一端后，必须同步另一端的配置、说明和回归测试；不能只改测试窗口或只改 QQ 运行层。源码包和 GitHub 是否同步属于独立发布步骤，只有用户明确要求时执行。

## 测试窗口验收方法

在“当前发言者”中切换昵称进行模拟：

1. 用甲发送一句话，2 秒内仍用甲发送同一话题，确认合并。
2. 用甲发送不同话题，确认拆成不同批次。
3. 用甲发送后切换乙，在同一时间窗口发送相近话题，确认可以合并但事件中仍能区分甲、乙。
4. 用甲发送后等待超过 3 秒，再发送第二句，确认分别生成回复。
5. 查看状态栏中的 `quiet2s`、`max3s` 和“同话题合并”标记。

本机规则只负责快速分组，不额外消耗 Luna 额度；每个最终批次仍由当前配置的 GPT-6 Luna High 生成凯尔希回复。

## 延迟优化约定

测试窗口会在回复状态中显示提示组装、模型调用和总链路耗时；QQ 运行层把不含聊天正文的阶段耗时写入对应 `runtime/*/latency-summary.jsonl`。当前所有消息恢复使用完整上下文与检索链，GPT-6 Luna High、Fast 关闭。Codex CLI 当前没有可验证的常驻多轮 Worker 模式，因此暂不复用旧会话，避免串入过期人格或其他群上下文。
